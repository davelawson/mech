# Instructions for AI assistants

- **Documentation:** record game behavior and rules in the matching `docs/` file: strategy screens and campaign rules in `docs/design.md`, combat behavior in `docs/combat-design.md`, combat numbers in `docs/combat-tuning.md`, model and paperdoll details in `docs/mech-models.md`, test groups and when to run them in `docs/testing.md`. `README.md` only gains setup steps, build/test/export commands, and new inputs in its Controls table.
- **Tests:** after changes, run only the test groups covering the changed files: `scripts/mech test <group...>` (the map from files to groups is in `docs/testing.md`). Run the full `scripts/mech test` only when shared code listed there changes or the user asks. The tests you run must pass before the work counts as done: fix failures, and if some still fail after a few attempts, say which ones fail and why instead of calling the work done. Put new tests in the group for the screen they exercise, and give a new screen its own group. Groups must not depend on each other's state.
- **Terminology:** use the project terms defined in `CONTEXT.md`.
- **Working mode:** check where you are working before changing files. Run `git rev-parse --path-format=absolute --git-dir --git-common-dir`; if the two paths differ, you are in a worktree, otherwise you are in the main checkout.
  - **Main checkout:** edit files only. Never commit, push, create branches or open pull requests; the user commits. A hook in `.claude/settings.json` blocks commits, pushes and pull requests here.
  - **Worktree:** you have full control of git in this worktree on any branch other than `main` or `master`: create and switch branches, commit, amend, rebase, push those branches and open pull requests. Commit as you go. Force-push only branches you created, with `--force-with-lease`. Never commit on, push to or rewrite `main` or `master`, and leave other worktrees, the main checkout and branches you didn't create alone. Merge a pull request only when the user asks you to, and only your own, when it isn't a draft and its checks pass; don't use `--delete-branch`, which fails in a worktree. The same hook blocks commits and pushes to `main` or `master` here.
    1. **Brief first.** Before any other work (reading code to understand the request is fine), rewrite the user's request as a brief: the goal, the acceptance criteria for this task, and what is out of scope. Make each criterion specific and checkable. List only criteria specific to this task; the standing criteria below apply to every task. Post the brief and end your turn until the user explicitly accepts it; silence or an unanswered question is not acceptance. If they change it, post the revised brief and wait again. The accepted brief is the source of truth for the work, the review and the pull request.
    2. Do the work. When it is done, the covering test groups must pass (see **Tests**).
    3. Run the `reviewer` agent, giving it the accepted brief. Fix every blocking issue it reports, then repeat from step 2. Stop after 3 review rounds.
    4. **Ideas update.** When everything else is done, propose updates to `IDEAS.md`: ideas this change implemented (remove), ideas it affects (reword), and new follow-ups or issues found during the work (add, under the matching section). List each proposed edit explicitly, or say you have none. Post the proposal and end your turn until the user explicitly responds; silence or an unanswered question is not a response. Apply only the edits the user approves, and commit them.
    5. Push the branch and open a pull request against `main`. The description states the accepted brief, the change, the test groups run and their results, the reviewer's final verdict, any minor issues left, and the `IDEAS.md` edits made. If tests still fail or the last review is a FAIL, open it as a draft and start the description with what is unresolved. Leave the pull request open for the user unless they asked you to merge it.

    **Standing criteria** for every worktree task: the covering test groups pass and new behavior has tests in the right group; game behavior and rules are recorded in the matching `docs/` file; project terms from `CONTEXT.md` are used; the change stays within the brief, with no unrelated edits.
- **Uncommitted changes:** before starting any non-planning work (editing files, running builds or tests), check `git status`. If there are uncommitted changes, stop and ask the user to confirm, saying explicitly that uncommitted changes exist and listing them briefly. Planning, reading and answering questions need no confirmation.
